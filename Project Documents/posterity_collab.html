01   Introduction

What This
System Does

Posterity's collaboration system is not a project management tool. It is a living, automated infrastructure that allows multiple builders to work on the same project across different sessions — without stepping on each other's work, without lengthy handoffs, and without ever losing context.

At its core, the system uses a single source of truth: the Posterity Project Context document. Every session begins by reading it. Every session ends by updating it. The context is what connects every builder, every Claude instance, and every build decision made across the entire project.

This document explains how that system works — how builders communicate through it, how conflicts are prevented, how creativity is tracked, and how the whole thing stays synchronized automatically.

"The context is not documentation. It is the project. Everything that has been decided, built, and planned lives there — and it moves forward with every session."

🔄
Fully Automated Sync

One command at the end of every session updates all locations — local files, OneDrive, Google Docs, session log — simultaneously.

⚡
Conflict Prevention

The context contains active build plans. Claude reads them at session start and flags any overlap before a single line of code is written.

🧠
AI-Native

Claude reads, updates, and reasons about the context automatically. Every session starts with full project awareness — no manual briefing required.

📊
Live Tracking

Contribution points, creativity gauges, collaboration tiers, and builder status are all tracked and updated automatically through the session log.

02   The Medium

The Context
Document

Every builder works from the same document. It is always current. It is always authoritative.

The Posterity Project Context is a living markdown document maintained across four synchronized locations: the local project folder, OneDrive, a Google Doc, and a generated PDF. When npm run sync runs at the end of a session, all four update simultaneously.

The document contains everything: product decisions, technical architecture, phase roadmap, brand copy, rules, collaboration status, and the active build plan. When a new session begins, the builder uploads the latest context to Claude. Claude reads it entirely before responding to anything else. This gives every session full project memory — regardless of which Claude instance, which builder, or how long since the last session.

03   The Workflow

Session
Workflow

Every session — yours or a collaborator's — follows the same sequence. No deviations. The workflow is what makes the system work.

Session Start

Pull latest context from Google Drive

Always start from the most current version. Never work from a cached or local copy without verifying it matches the Google Doc version number.

Upload context to Claude Project Instructions

Open the Posterity project in Claude.ai and paste the full context into the Project Instructions. This gives Claude complete project memory for the session.

Read the notification bar

Check the status indicators at the top of the context. If yellow or red, review recent session notes before planning any work.

Declare your build plan to Claude

Before writing a single line of code, tell Claude what you intend to build. Claude will read the current context, check for conflicts with other active plans, and confirm it is safe to proceed.

Work from the Collaborative Phase section

Auxiliary builders must only work on items listed in the Collaborative Phase section of the context. This section is auto-generated each session and lists everything safe to build in parallel with the primary phase.

Session End

Fill in session-notes.md

Document key decisions made, what was built, what was discussed, and next session priorities. This feeds the session log automatically.

Run npm run sync

One command handles everything: updates local context, copies to OneDrive and Project Documents, regenerates PDF, appends session notes to Google Session Log Doc, updates Google Context Doc, and commits and pushes to GitHub.

Update Claude Project Instructions

Copy the updated context and paste into the Posterity Claude Project Instructions. This ensures the next session starts with full current memory.

Deviations from this workflow require written notification to the project administrator at posterity.admin@gmail.com with a clear explanation of the reasoning. The workflow exists to protect every builder's work — not just yours.

04   Builder Roles

Main Builder &
Auxiliary

At any given time, one builder holds Main Builder status. All others are Auxiliary. Roles can switch — but only through a declared request, not unilaterally.

👑
Main Builder

Owns the primary phase build. Works directly on whatever the current Phase Roadmap item is. There is only ever one Main Builder active at a time.

🔧
Auxiliary Builder

Works exclusively from the auto-generated Collaborative Phase section. Builds parallel items that do not conflict with the primary phase work.

Switching Roles

Either builder can request a role switch at any time by posting a request in the notification section of the context. The current Main Builder must acknowledge the switch before it takes effect. This prevents two people from unknowingly working as Main Builder simultaneously — which is the primary source of build conflicts.

For long multi-session builds, declare the full plan in the context upfront. As long as no builder deviates from their declared plan, no conflicts arise across sessions — even without real-time coordination.

05   Intensity Tiers

Collaboration
Tiers

The collaboration tier is a live gauge of how actively the project is being worked on. It lives in the notification bar and updates automatically based on session frequency.

Solo

One builder, no coordination needed

Standard context update at end of session. No special protocols required.

Low

Occasional collaboration

Async context updates sufficient. Pull latest context at session start. Session log review recommended.

Medium

Regular collaboration

Daily context syncs strongly recommended. Declare build plans before starting. Review session notes carefully.

Heavy

Frequent collaboration

Context update required after every build segment — not just at session end. Treat context as a live document.

Simultaneous

Two or more builders working at the same time

Real-time coordination required. Declare plans explicitly. Conflict check mandatory before every build action. Context updates after every segment, no exceptions.

08   Creative Backlog

Horizon
Builds

Ideas that emerge during the build process and could change the way Posterity works, looks, or feels. Not tabled because they are unimportant — tabled because they haven't found their phase yet.

Horizon Builds sits above the Phase Roadmap in the context. Items here are high priority creative sparks that are actively being considered for roadmap inclusion. They are not discarded ideas. They are the next evolution of the product waiting to be built.

Any builder can add to Horizon Builds during a session. Claude will flag items that could affect the current phase build and surface them at session start. Items that graduate into a phase get moved to the roadmap automatically during the context update.

Horizon Builds is where Posterity becomes more than what it was planned to be. It is the space where the product grows beyond its original vision — session by session, idea by idea.

💡
How to Add

Tell Claude during any session. It will be formatted and added to the Horizon Builds section during the end-of-session context update.

🚀
How Items Graduate

When a Horizon Build item is ready for a phase, the team declares it in the context and it moves to the roadmap in the next update.

📊
Creativity Credit

Adding a Horizon Build item earns creativity points on your Posterity ID. Phase-changing ideas earn the highest point value in the system.

09   Infrastructure

The MCP
Layer

Model Context Protocol servers are the automation backbone of the collaboration system. They connect Claude in Cursor directly to GitHub, Supabase, and Google Docs — enabling fully automated syncing without manual steps.

G

GitHub MCP

Connects Claude to the private Posterity repository. Enables direct code commits, branch management, and push operations without leaving the Cursor Agent. Contact project administrator for repository access.

S

Supabase MCP

Connects Claude to the Posterity database. Enables schema inspection, query execution, and database operations directly from the Agent. Requires a Supabase personal access token from the project dashboard.

D

Google Docs MCP

Connects Claude to the Posterity Context Doc and Session Log Doc on Google Drive. Enables automatic context updates and session log appends at the end of every session via npm run sync. Requires the shared service account key file from the project administrator.

Full setup instructions for all MCP servers are provided in the Posterity Collaboration Setup Guide. Each collaborator creates their own GitHub and Supabase tokens. The Google Docs service account key is shared and provided by the project administrator.

Contact posterity.admin@gmail.com to receive the Google Docs service account key, GitHub repository access, and Supabase project credentials needed to begin collaborating.
